# 西湖区全量住宅数据库与决策应用实施计划

> 版本：0.1  
> 制定日期：2026-09-19  
> 项目范围：杭州市西湖区住宅小区数据底座、后端服务与前端决策工作台  
> 目标：形成可持续更新、来源可追溯、结论可解释的购房决策基础设施

## 1. 建设目标与范围

本阶段的核心不是抓取尽可能多的网页，而是建立一套稳定的数据产品：每个小区有唯一身份，所有事实有来源和有效期，所有指标可回算，所有评分可解释。

### 1.1 “全量”的工作定义

默认范围为采集时点杭州市西湖区行政边界内，可识别且存在住宅用途的已建成、在售或明确在建项目，包括商品住宅、住宅性质公寓、房改房、经济适用房、安置房等；非住宅商办、宿舍、酒店式公寓单独标记，不混入普通住宅比较。

以下边界必须显式管理：

- 西湖风景名胜区受托管理区域与西湖区行政区的关系；
- 之江、双浦等市场板块与行政街道边界的差异；
- 同名小区、分期项目、东西区、组团及共用物业项目；
- 已拆迁、待交付、停工、用途不明确的项目。

首轮全量率的分母以至少两个独立来源合并去重后的小区主清单为准。项目不承诺获得所有逐套真实成交；无法取得的数据应标记为未知，而不是以挂牌信息代替。

### 1.2 首期交付物

1. 西湖区住宅小区主数据库及字段字典。
2. 原始、清洗、指标三层数据管道和质量报告。
3. 小区检索、地图、详情、对比、评分、来源追溯 API。
4. 面向桌面和移动端的地图与小区决策工作台。
5. 数据更新任务、失败告警、人工复核队列和操作手册。

### 1.3 非目标

- 绕过登录、验证码、robots 或平台技术限制采集数据；
- 对未来房价给出确定性预测；
- 将规划学校、规划地铁当作已兑现配套；
- 批量存储业主姓名、电话、身份证、门牌交易记录等个人信息；
- 用一个不透明总分代替分项证据。

## 2. 总体架构

```text
官方开放数据 / 官方网页与文件 / 合规地图 API / 授权市场数据 / 人工核验
                              │
                              ▼
                  采集任务与原始快照 Raw
                              │
                    解析、标准化、实体匹配
                              │
                              ▼
       SQLite（本地）/ MySQL 8.x（生产）（核心事实、空间对象、时间版本）
                   │                     │
             指标计算与评分          数据质量与复核队列
                   │                     │
                   └─────────┬───────────┘
                             ▼
                     FastAPI 后端服务
                             │
                             ▼
             Next.js 决策工作台 / 地图 / 对比 / 管理端
```

建议技术栈：

- 数据库：Mac 本地开发使用 SQLite，腾讯云生产使用 MySQL 8.x；迁移使用 Alembic。
- 数据采集与后端：Python、FastAPI、SQLAlchemy、Pydantic。
- 定时任务：首期使用独立 worker + 系统定时任务；任务量增加后再引入任务队列或编排平台。
- 缓存：首期使用聚合表和 HTTP 缓存；需要高并发或路径计算缓存时再增加 Redis。
- 前端：Next.js + TypeScript；表格、图表和地图组件均保持可替换。
- 地图：优先使用合规地图 API，并统一处理 GCJ-02/WGS84 坐标系及授权展示要求。
- 文件证据：本地对象目录起步，数据库只保存哈希、元数据和位置；以后可迁移至对象存储。

架构原则是先保持单体应用和单数据库，避免在数据口径尚未稳定时引入微服务。

### 2.1 本地与生产数据库策略

本地默认不要求安装数据库服务，应用首次启动时创建 `data/house_analysis.db`。SQLite 开启外键约束和 WAL 模式，适合单机开发、采集验证和自动化测试。生产环境通过连接配置切换到腾讯云 MySQL，不在业务代码中判断数据库类型。

为了控制 SQLite 到 MySQL 的迁移风险，首期遵循以下兼容约束：

- 只使用 SQLAlchemy 跨数据库类型和查询能力，避免依赖 SQLite 专属 SQL；
- 主键使用应用生成的 ULID/UUID 字符串，不依赖数据库自增连续性；
- 时间统一以 UTC 保存，接口按用户时区显示；
- 布尔值、枚举和 JSON 均由 ORM 做统一映射，重要筛选字段不藏在 JSON 中；
- 金额、单价、经纬度使用定点数，不使用浮点数保存财务值；
- 索引长度、唯一约束和字符串排序规则以 MySQL 限制为基准设计；
- 不使用数据库触发器、存储过程、物化视图或供应商专属全文检索作为核心逻辑；
- 每次数据库迁移都同时在 SQLite 和 MySQL 8.x 的持续集成环境执行。

空间数据的权威字段使用 `longitude`、`latitude`、边界框、`geohash` 和 GeoJSON。首期由应用层完成 Haversine 距离、视口过滤和少量点面判断。部署到 MySQL 后可以增加 `POINT SRID 4326`、空间索引和派生几何列加速查询，但它们只是性能层，不替代可移植的权威字段。若将来出现大规模复杂空间分析需求，再单独评估 PostGIS，而不影响当前业务模型。

开发环境支持两种模式：

| 模式 | 数据库 | 用途 |
|---|---|---|
| 默认零依赖模式 | SQLite 文件 | 日常 Mac 开发、演示、单元测试 |
| 生产兼容模式 | 本机或容器 MySQL 8.x | 发布前迁移、SQL、索引和性能验证 |

生产发布前必须在 MySQL 模式完成全量导入演练，不允许仅凭 SQLite 测试结果上线。

生产迁移采用应用级导入工具，而不是直接转换 SQLite 文件：先对腾讯云 MySQL 执行 Alembic 建表，再按依赖顺序批量导入经过校验的数据，最后核对各表行数、唯一键、外键、哈希和关键指标。可重新采集的 Raw/Core 数据优先从原始快照重放；用户收藏、备注和决策方案则通过带版本的 JSON 导出/导入保留。

## 3. 工作流一：构建数据库

### 3.1 数据分层

| 层级 | 目的 | 内容 | 是否允许人工修改 |
|---|---|---|---|
| Raw 原始层 | 保存证据、支持重放 | 原始 JSON/HTML/PDF 元数据、抓取时间、哈希、请求参数 | 否 |
| Core 核心层 | 形成统一事实 | 小区、楼栋、学校、POI、交通、市场事实及版本 | 通过审核流程 |
| Metric 指标层 | 支撑筛选和比较 | 近 3/6/12 月成交、生活圈、通勤、完整率、分项评分 | 由规则重算 |
| User 用户层 | 保存个人决策 | 家庭画像、权重、收藏、备注、看房记录 | 是 |

### 3.2 核心实体

#### 地理与小区

- `administrative_area`：区、街道、社区行政边界及版本。
- `market_area`：市场板块及人工维护的版本化边界。
- `community`：小区稳定主键、标准名、类型、状态、中心点和边界。
- `community_alias`：别名、旧名、平台名、来源和匹配状态。
- `community_phase`：一期、二期、组团等子项目。
- `building`：楼栋、用途、层数、电梯、建成年份等；允许首期不完整。
- `community_fact`：开发商、物业、容积率、绿化率、户数、车位等带有效期事实。

#### 来源与证据

- `data_source`：来源机构、入口、许可/使用限制、可靠性级别。
- `ingestion_run`：每次采集的起止时间、版本、结果和错误。
- `raw_snapshot`：原始内容地址、内容哈希、观察时间和解析状态。
- `source_record`：来源记录 ID 与内部实体 ID 的映射。
- `evidence`：支持某一事实或人工判断的网页、文件、截图或备注。
- `review_task`：实体冲突、字段异常、过期信息和人工核验状态。

#### 市场

- `market_observation`：成交/网签/挂牌/调价/租赁等观察记录，明确口径。
- `listing_snapshot`：合规获取的挂牌快照，用来源房源 ID 去重。
- `community_market_monthly`：小区月度成交量、价格分布、挂牌量、成交周期等聚合。
- `area_market_monthly`：板块和行政区对照指标。

市场指标至少保存样本数、中位数、25/75 分位数、均值、口径和数据截至日。样本不足时隐藏或降级置信度。

#### 教育、交通和生活配套

- `school`：学校、学段、校区、集团、状态和坐标。
- `school_catchment_rule`：学年、官方地址描述、原文、有效期。
- `community_school_mapping`：小区与学校的年度映射、匹配方式、置信度和人工确认。
- `poi`：商业、医疗、公园、菜场、养老、文体等设施。
- `transit_station`、`transit_line`：车站、线路及运营/在建/规划状态。
- `accessibility_metric`：小区至设施或目的地的步行、公交、驾车时间和计算时点。

#### 环境、规划和风险

- `planning_project`：规划项目、阶段、批准文件、预计时间和几何范围。
- `environment_observation`：空气、噪声、水系、绿地、内涝等观察。
- `risk_feature`：高架、铁路、变电设施、污染源等空间风险及证据。
- `community_review`：物业、停车、维护和现场感受；区分事实与主观评价。

#### 指标和评分

- `metric_definition`：指标定义、单位、计算方法、上下界和版本。
- `community_metric_snapshot`：小区在指定日期的指标值、置信度和输入版本。
- `score_profile`：自住、学区、通勤、改善、资产安全或用户自定义权重。
- `community_score`：各维度得分、总分、敏感项和规则版本。

### 3.3 首版字段优先级

P0 字段用于首版全量覆盖：

- 标准名、别名、地址、坐标、街道、社区、板块；
- 住宅类型、建成年代、开发商、物业、户数、楼栋数、电梯；
- 近 3/6/12 月市场样本量与价格分布；
- 当学年小学、初中映射及官方来源；
- 地铁步行时间、公交覆盖、基础生活 POI、医疗、公园；
- 数据更新时间、完整率、来源、置信度和待核验项。

P1 再补充容积率、绿化率、车位比、梯户比、物业费、户型分布、租金、成交周期、规划和环境风险。楼栋与逐房源粒度放在有合法数据和实际决策需要时推进。

### 3.4 实体消歧

小区匹配不能只靠名称。候选匹配分数至少组合：标准化名称、别名、地址、空间距离、开发商、建成年代和来源上下文。

规则建议：

- 高置信度自动合并；
- 中置信度进入人工复核；
- 低置信度建立新实体；
- 已确认的合并和拆分均写入审计记录，禁止直接覆盖历史。

### 3.5 数据质量门槛

| 指标 | 首期目标 |
|---|---:|
| 小区主清单覆盖率 | ≥ 95% |
| 标准地址与坐标完整率 | ≥ 98% |
| 街道/板块归属完整率 | ≥ 98% |
| 基础属性 P0 完整率 | ≥ 85% |
| 当年学区映射覆盖率 | ≥ 90%，其余明确待核验 |
| 外部事实来源可追溯率 | 100% |
| 市场指标口径标注率 | 100% |
| 自动实体合并抽检准确率 | ≥ 98% |

每次发布数据版本前生成质量报告，未达到门槛的数据域不得显示为确定结论。

### 3.6 更新频率

- 挂牌、成交公开数据：每日或每周，取决于许可和来源稳定性。
- 小区月度市场指标：月更。
- POI 与通勤：季度更新；用户重点通勤可按需计算并缓存。
- 学区：每学年发布后全量更新，调整公告事件驱动更新。
- 规划、政策、交通状态：事件驱动，至少月度巡检。
- 小区静态属性：半年巡检，用户纠错即时进入复核。

## 4. 工作流二：后端服务

### 4.1 服务模块

1. **目录服务**：行政区、板块、小区、学校和 POI 查询。
2. **市场服务**：成交、挂牌、趋势、可比小区和流动性指标。
3. **空间服务**：地图范围查询、附近设施、距离和通勤。
4. **教育服务**：按学年查询服务区、映射依据和风险提示。
5. **指标服务**：指标定义、快照、置信度和数据新鲜度。
6. **评分服务**：硬约束、权重评分、敏感性分析和排序解释。
7. **用户决策服务**：画像、收藏、对比组、备注和看房记录。
8. **数据治理服务**：来源、任务状态、问题队列、人工审核和重算。

### 4.2 首版 API

| 方法与路径 | 用途 |
|---|---|
| `GET /areas` | 行政区与市场板块 |
| `GET /communities` | 分页、筛选、排序和地图框选 |
| `GET /communities/{id}` | 小区完整详情 |
| `GET /communities/{id}/market` | 市场趋势、样本和口径 |
| `GET /communities/{id}/schools?school_year=` | 当年学区及证据 |
| `GET /communities/{id}/amenities` | 生活圈与可达性 |
| `GET /communities/{id}/risks` | 风险与规划信息 |
| `GET /communities/{id}/sources` | 字段级来源与更新时间 |
| `POST /compare` | 批量比较小区 |
| `POST /score` | 按画像和权重计算分项分数 |
| `POST /routes` | 计算或读取通勤缓存 |
| `GET /data-quality` | 数据版本、完整率和新鲜度 |

管理端另设受保护接口，用于实体合并、字段纠错、学区确认、任务重跑和指标重算。

### 4.3 查询和计算约束

- 列表接口使用游标或稳定分页，地图查询按视口和缩放级别聚合。
- 所有时间序列明确时区、统计周期和缺失值；未知值不能转为零。
- 评分请求必须返回分项、权重、规则版本、输入数据日期和置信度。
- 路径结果保存起终点、出发时段、交通方式、地图供应商和计算日期。
- 学区接口默认返回当前学年，但支持历史查询和变更对比。
- 公开接口不暴露地图密钥、内部采集凭证或原始个人信息。

### 4.4 非功能要求

- 常用小区列表和详情 P95 响应时间低于 500ms，不含实时路径供应商调用。
- 关键写操作幂等；采集任务可重试且不会制造重复事实。
- 自动生成 OpenAPI 文档，核心服务具备单元和集成测试。
- SQLite 开发库使用安全复制/备份接口保存快照；腾讯云 MySQL 开启自动备份，并定期验证逻辑导出和恢复。
- 结构化日志包含请求 ID、数据版本和任务运行 ID。
- 单用户首期仍需隔离用户数据，并支持完整导出和删除。

## 5. 工作流三：前端展示服务

### 5.1 页面结构

#### 1. 数据概览

- 当前小区数量、覆盖街道、数据完整率和最近更新时间；
- 市场总体趋势及样本口径；
- 过期、缺失和待核验数据提示。

#### 2. 地图找小区

- 地图与列表联动，支持框选、聚合和条件筛选；
- 筛选建成年代、总价/单价、市场活跃度、学区、地铁时间、商业医疗和风险；
- 切换行政街道、市场板块、学区和通勤等时圈图层；
- 运营、在建、规划设施使用不同视觉语义。

#### 3. 小区详情

- 基础档案与位置；
- 近 3/6/12 月市场卡片和趋势；
- 当学年小学、初中及规则原文；
- 交通、商业、医疗、公园生活圈；
- 居住品质、规划和风险；
- 每个模块可展开查看来源、日期、样本和置信度。

#### 4. 小区对比

- 支持 2–5 个小区并排；
- 先显示硬约束是否通过，再显示分项得分；
- 突出差异、数据缺口和结论敏感项；
- 可保存为一个家庭决策方案。

#### 5. 我的决策方案

- 预算、家庭成员、目的地、硬约束和偏好权重；
- 收藏池、淘汰原因、看房记录和待核验风险；
- 权重调整后的排名变化，而不是固定“最佳小区”。

#### 6. 数据与规则

- 数据来源、版本、更新计划和质量报告；
- 指标定义、评分公式和政策适用日期；
- 纠错提交和处理状态。

#### 7. 数据管理端

- 采集运行、错误日志、数据异常、实体匹配和人工复核；
- 学区映射审核、来源失效检查、指标重算和版本发布。

### 5.2 核心交互原则

- 任何价格数字旁显示“成交/网签/挂牌”口径及时间范围。
- 样本不足时显示样本数和低置信提示，不绘制误导性平滑曲线。
- 学区固定显示学年、官方来源和“非入学承诺”提示。
- 总分必须能逐层展开到指标、原始事实和权重。
- 颜色不能单独承担风险含义，并满足移动端和基本无障碍要求。
- 地图之外始终提供表格视图，便于排序、核验和导出。

### 5.3 前端验收

- 用户能在 3 分钟内从全区缩小到 20 个以内候选小区；
- 能在一个页面理解某小区的数据日期、市场样本、学区和主要风险；
- 能比较 2–5 个小区，并看见每个差异的计算依据；
- 移动端可完成收藏、备注和现场核验；
- 无来源或过期数据不得以正常确定状态展示。

## 6. 实施阶段与里程碑

以下按 1–2 名工程人员估算；数据授权、地图密钥和人工核验时间可能影响进度。

### 阶段 0：范围冻结与技术底座（第 1 周）

- 冻结西湖区边界、小区类型和市场口径。
- 建立工程目录、SQLite 默认开发环境、MySQL 生产兼容测试、数据库迁移和配置管理。
- 完成字段字典 v1、来源登记表和数据许可清单。

**出口条件**：Mac 无需安装数据库服务即可一键启动后端和空白前端；同一迁移可在 SQLite 与 MySQL 8.x 执行；关键口径无未决歧义。

### 阶段 1：小区主数据（第 2–3 周）

- 接入至少两个小区名录来源。
- 完成地址规范化、地理编码、别名和实体匹配。
- 建立人工复核页面或脚本。
- 生成首版覆盖率和重复率报告。

**出口条件**：主清单覆盖率 ≥95%，坐标完整率 ≥98%，抽检合并准确率 ≥98%。

### 阶段 2：教育、交通和生活配套（第 4–5 周）

- 导入学校、年度学区文件和小区映射。
- 导入地铁/公交/POI，计算基础生活圈。
- 建立学区及空间数据的来源追溯。

**出口条件**：用户可通过 API 查询小区的当年学校、地铁、医疗、商业和公园，并看到证据。

### 阶段 3：市场与指标体系（第 6–7 周）

- 接入合规市场数据，区分成交、网签和挂牌。
- 生成月度聚合、流动性、样本置信度和数据新鲜度指标。
- 完成指标定义与版本化评分引擎。

**出口条件**：价格趋势可回溯、可重算，任何图表不会混用数据口径。

### 阶段 4：后端与前端决策闭环（第 8–10 周）

- 完成检索、地图、详情、对比、评分和来源接口。
- 完成地图找房、小区详情、对比、决策方案及数据说明页面。
- 加入家庭目的地、硬约束和自定义权重。

**出口条件**：能够用真实家庭画像从全区筛选、查看证据、比较并保存候选。

### 阶段 5：质量、运维与试运行（第 11–12 周）

- 建立定时更新、失败告警、备份恢复和数据发布流程。
- 完成 SQLite 到腾讯云 MySQL 的全量迁移演练及数据一致性报告。
- 邀请真实用户用 3–5 个购房场景验收。
- 修复高优先级数据问题，记录剩余数据缺口。

**出口条件**：连续两轮更新任务成功，核心流程无阻断问题，质量报告达到首期门槛。

## 7. 并行工作与依赖

三条主线并非完全串行：

| 数据库 | 后端 | 前端 |
|---|---|---|
| 先冻结主键和字段字典 | 用模拟数据建立 API 合约 | 用模拟 API 完成页面骨架 |
| 接入小区和空间数据 | 实现目录、空间查询 | 完成地图、列表、详情 |
| 接入市场和学区 | 实现指标、评分、来源 | 完成趋势、对比、证据展示 |
| 建立质量与复核 | 实现管理端接口 | 完成数据管理与异常页面 |

关键依赖是“小区唯一 ID、时间版本和来源模型”。这三项未稳定前，不应大规模开发评分和图表。

## 8. 测试与验收策略

### 数据测试

- 主键、唯一约束、时间区间和空间合法性测试；
- Alembic 迁移在 SQLite 和 MySQL 8.x 均可从空库执行到最新版本；
- 使用同一份固定样例对两种数据库运行核心查询，结果必须一致；
- 小区坐标必须落在合理行政边界内，否则进入复核；
- 月度成交量不得小于零，分位数顺序必须正确；
- 学区映射必须绑定学年和官方证据；
- 同来源记录重复导入不产生重复事实；
- 原始快照到指标值可完整追溯。

### 服务测试

- API 合约、权限、分页、筛选、空间查询和幂等性；
- 指标和评分的固定样例回归测试；
- 第三方地图/API 超时、限流和不可用时的降级；
- 数据版本切换和历史查询。

### 用户验收场景

1. 双职工家庭按两个工作地筛选通勤小区。
2. 有入学需求的家庭核验目标学年学区及分流风险。
3. 改善家庭比较新旧小区的居住品质与流动性。
4. 用户发现错误后提交证据，管理员审核并发布修订版本。

## 9. 合规与安全

- 每个数据源登记公开范围、许可、调用限制、缓存和再展示条件。
- 优先使用官方开放数据、公开文件、正式 API 和授权数据。
- 不绕过访问控制；来源明确禁止自动采集时改为人工引用或放弃。
- 只保存决策必需的用户信息，敏感配置使用环境变量或密钥管理。
- 对外展示统计数据时避免反推出具体自然人或逐户交易信息。
- 地图数据遵守供应商坐标、配额、展示和缓存要求。

## 10. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 小区级真实成交不完整 | 估值和流动性可信度下降 | 展示样本和置信度，使用板块对照，不以挂牌冒充成交 |
| 数据源页面变化或下线 | 更新中断 | 保存原始快照、解析器测试、备用来源与人工导入 |
| 学区地址描述难以自动匹配 | 错误教育结论 | 自动候选 + 人工审核，按学年版本化 |
| 同名/分期实体误合并 | 多域数据污染 | 多特征匹配、审计记录、可逆合并 |
| 地图调用费用或配额 | 通勤计算受限 | 缓存、批量计算、重点目标按需更新 |
| 评分制造虚假精确 | 用户过度信任 | 分项展示、敏感性分析、数据缺口和反对理由 |
| 全量范围持续膨胀 | 工期失控 | 先保证 P0 小区级覆盖，楼栋和逐房源后置 |

## 11. 第一迭代任务清单

实施开始后的首个迭代只处理底座，不接入高风险平台抓取：

1. 初始化 SQLite/MySQL 双环境、FastAPI、Next.js 工程和本地启动脚本。
2. 建立 `data_source`、`community`、`community_alias`、`source_record`、`raw_snapshot`、`ingestion_run` 和 `review_task`。
3. 定义西湖区行政/市场空间边界及版本。
4. 制作首批小区名录导入模板与地址标准化管道。
5. 实现 `/communities`、`/communities/{id}` 和 `/data-quality`。
6. 制作小区列表、地图占位、详情和数据质量页面。
7. 用一批真实小区完成导入、消歧、查询、展示和来源追溯的端到端验证。

完成该迭代后，再根据实际来源可用性确定市场数据自动化上限，而不是先假设所有网站都能稳定抓取。
