# 数据流程与开源项目方法调研

> 调研日期：2026-09-29  
> 调研目的：不是复用开源项目的数据或直接搬用爬虫，而是结合本项目的购房决策目标，提炼其核心逻辑、任务流程和工程模式。

## 1. 结论

本项目最值得从开源项目借鉴的不是“如何抓某个网站”，而是以下五种能力：

1. **空间分片发现**：把全区大查询拆成可重复、可核对的小任务；
2. **可靠采集执行**：限速、重试、缓存、断点续跑、任务指标和失败重放；
3. **原始记录与规范事实分层**：采集结果先作为证据保存，再解析、标准化和发布；
4. **跨来源实体解析**：以名称、地址、坐标、年代等组合证据识别同一小区；
5. **时间化观察**：同一房源或小区在不同时间的快照生成调价、上下架和数据新鲜度事件。

这些能力应重新实现为当前项目的数据管道，与现有 `data_source`、`ingestion_run`、`raw_snapshot`、`source_record`、`community` 和 `review_task` 模型衔接，而不是把外部仓库当作数据源依赖。

## 2. 项目需求与可借鉴逻辑

### 2.1 建立西湖区小区候选全集

**项目需求**

- 大查询不能因一次 504 导致整批回滚；
- 能回答“哪些空间范围完成、哪些失败、哪些尚未执行”；
- 同一任务重复执行不产生重复候选；
- 最终结果必须按版本化行政边界裁剪，而不是只信来源的区域标签。

**可借鉴方法**

- [OSMnx](https://github.com/gboeing/osmnx) 会先把大型 polygon 投影到适合计算面积的坐标系，超过阈值时切成多个子多边形，再逐片请求 Overpass；请求键可缓存，并根据 Overpass 状态决定等待时间。它解决的是“大空间查询如何稳定执行”，而不是住宅业务本身。
- [osmdata](https://github.com/ropensci/osmdata) 将 bbox/polygon 查询、OSM 要素选择、结果裁剪和元数据保留拆成明确步骤，适合参考其“查询范围”和“最终有效范围”分离的思路。
- [hz-lianjia-scrawler](https://github.com/ChrisLinn/hz-lianjia-scrawler) 体现了“行政区 → 小区 → 房源”的两级发现流程，并明确指出按行政区遍历存在页数上限。这提示本项目不能把单一路径返回的结果数当成覆盖率分母。

**本项目落地流程**

```text
行政边界版本
  → 生成稳定分片（partition_id + geometry + boundary_version）
  → 每片生成请求计划
  → 保存原始响应与请求哈希
  → 解析 OSM node/way/relation
  → 以来源 ID 去重
  → 合并所有分片
  → 按行政边界做本地点面过滤
  → 进入小区候选与人工复核队列
```

**验收指标**

- 计划分片数、成功数、失败数和跳过数可以对账；
- 任意失败分片可单独重跑；
- 相同边界版本与查询版本重复运行不产生重复 `source_record`；
- 分片边界重叠产生的 OSM 对象能按 `osm_type/osm_id` 合并；
- 任务级报告包含元素数、无名称率、坐标完整率和边界外剔除数。

### 2.2 可靠执行与可观测性

**项目需求**

- 公共接口出现 429、5xx 或超时时能够退避并恢复；
- 失败不能被静默吞掉，也不能只在日志里留下不可统计的信息；
- 采集与落库解耦，避免一个解析或写入错误毁掉整个批次。

**可借鉴方法**

- [Jye10032/Lianjia-crawler](https://github.com/Jye10032/Lianjia-crawler) 的新版并行流程包含指数退避与抖动、全局和分区令牌桶、独立写入队列，以及按区域、页码记录状态码、响应大小和耗时的 metrics。与特定网站无关的这些机制值得借鉴。
- OSMnx 会在请求前检查 Overpass slot 状态，缓存相同请求，并对 429/504 延迟后重试。其核心启示是“服务端容量也是调度输入”，不能只在失败后盲目重试。

**本项目落地流程**

- 新增持久化分片状态，至少包含 `pending/running/succeeded/retryable_failed/permanent_failed`；
- 重试策略按异常分类：429/502/503/504/超时可重试，解析契约错误和 4xx 参数错误直接失败；
- 使用有上限的指数退避和抖动，不使用无限递归重试；
- 每次尝试记录 endpoint、开始/结束时间、HTTP 状态、字节数、元素数、异常类型和重试序号；
- 原始响应成功保存后再进入解析阶段，使解析器升级可以离线重放，不必再次访问来源；
- 初期采用低并发甚至串行分片，先验证正确性和可恢复性，再按指标决定是否提高并发。

**不照搬的部分**

- 不使用登录 Cookie、代理轮换或验证码处理；
- 不把异常捕获后简单返回空列表，因为“真实无数据”和“采集失败”必须区分；
- 不只写 CSV metrics，而是把运行状态写入数据库，同时支持导出报告。

### 2.3 Raw、Core 与 Metric 分层

**项目需求**

- 外部页面或接口变化后可以重新解析历史原始记录；
- 事实更新不能覆盖来源证据；
- 一个来源错误不能直接污染已核验主数据；
- 评分和指标必须能追溯到输入版本。

**可借鉴方法**

- 房产爬虫通常会先解析列表字段，再写 CSV/JSON 或数据库；这说明“抓取—解析—存储”是基本流程，但多数仓库把三者耦合在一个函数里，缺少历史重放和字段级来源。
- 本项目应保留这些仓库的字段解析思想，但采用更严格的分层：Raw 保存原样证据，Source Record 保存来源语义，Core 保存审核后的统一事实，Metric 只保存可重算输出。

**本项目落地流程**

```text
HTTP/File 输入
  → raw_snapshot（不可人工改写、内容哈希去重）
  → parser_version 解析
  → source observation（保留来源字段、单位和口径）
  → normalize（名称、金额、面积、时间、坐标系）
  → entity resolution
  → core fact（有效期、置信度、审核状态）
  → metric snapshot（规则版本、输入版本、样本数）
```

解析器必须使用固定样例回归测试。字段消失、页面结构变化或数值异常时进入 `review_task`，不能把缺失值转成零。

### 2.4 小区实体解析与消歧

**项目需求**

- 处理同名小区、一期/二期、东西区、别名和旧名；
- 避免仅因名称相同就合并，也避免同一小区被多个来源重复创建；
- 每次自动合并都能解释并可撤销。

**可借鉴方法**

- [dedupe](https://github.com/dedupeio/dedupe) 使用人工标注的匹配/不匹配样本，学习名称、地址等字段的组合规则，适合数据达到一定规模后生成候选对。
- [Splink](https://github.com/moj-analytical-services/splink) 强调 blocking、字段比较等级、概率权重和诊断图，适合多来源、大数据量、字段较丰富时使用。
- 两者都表明实体解析不是一个名称相似度函数，而是“先缩小候选对，再组合多字段证据，再设自动/人工阈值”。

**本项目分阶段策略**

1. 当前阶段使用确定性候选规则：标准化名称或别名命中，并结合距离、地址、开发商、建成年代；
2. 输出每个字段的匹配结果和总置信度，而不是只保存最终分数；
3. 高置信度自动关联，中置信度进入人工复核，低置信度建立新实体；
4. 积累至少 200 对人工标注样本后，再比较现有规则与 dedupe/Splink 的准确率和召回率；
5. 合并与拆分写入审计记录，历史来源映射不直接删除。

**验收指标**

- 固定标注集上分别报告 precision、recall，不能只报告总体 accuracy；
- 自动合并 precision 优先，目标 ≥98%；
- 同名远距离、同址不同期、别名同小区等边界案例有回归测试；
- 人工复核结果能够反哺规则版本，但规则升级不静默改写历史结论。

### 2.5 房源与市场的时间化观察

**项目需求**

- 区分挂牌、调价、下架、重新挂牌、网签和成交；
- 同一房源重复抓取不产生多套房源，却要保留变化历史；
- 所有价格趋势都必须保留样本量、口径和时间窗。

**可借鉴方法**

- 杭州及通用链家项目通常分别遍历小区、在售、租赁和成交数据，并保存总价、单价、挂牌时间、成交时间等字段。可借鉴的是“对象分层”和“不同业务状态分开采集”，不是页面解析代码。
- Jye 项目的逐页落盘与任务 metrics 可转化为本项目的快照完成度判断，避免部分分页成功时误以为得到了完整市场样本。

**本项目落地流程**

```text
来源房源 ID / 稳定指纹
  → listing identity
  → listing_snapshot（观察时点的完整状态）
  → 相邻快照差异
  → listing_event（首次出现/调价/下架/重现）
  → 与明确成交或网签记录独立关联
  → community_market_monthly
```

市场聚合只有在分区采集完成度达到门槛后才能发布；否则标记为部分样本。挂牌快照永远不能推断为成交。

### 2.6 从数据工程连接到购房决策

开源房产项目常止步于均价图表，而本项目需要把数据管道继续连接到家庭决策：

| 数据产物 | 决策用途 | 必须保留的解释 |
|---|---|---|
| 小区主数据 | 建立观察池、避免重复候选 | 来源、匹配依据、核验状态 |
| 学区年度事实 | 核验目标学年教育条件 | 学年、官方原文、地址适用范围 |
| 路网与 POI | 门到门通勤和生活可达性 | 交通方式、出发时段、计算日期 |
| 挂牌/成交观察 | 可比案例与流动性 | 口径、样本数、时间窗、置信度 |
| 风险与规划 | 红旗核验和情景变化 | 当前/在建/规划、证据与关闭状态 |
| 数据质量 | 判断结论能否使用 | 完整率、新鲜度、失败分片、待复核项 |

因此采集成功不等于产品完成。只有当候选能够展示事实、证据、缺口和对家庭约束的影响时，才算形成端到端价值。

## 3. 推荐的数据管道接口

下一版采集代码建议采用来源适配器，而不是为每个来源复制一套端到端脚本：

```python
class SourceAdapter:
    def discover_partitions(self, scope, boundary_version): ...
    def build_requests(self, partition): ...
    def fetch(self, request): ...
    def parse(self, raw_snapshot, parser_version): ...
    def normalize(self, source_records): ...
    def identity_keys(self, record): ...
```

通用执行器负责：状态机、限速、重试、缓存、原始快照、指标和失败重放；适配器只负责来源特有的请求与解析。这样 OSM、政府文件、人工 CSV 和未来授权数据可以共享同一条治理链路。

建议补充一个 `ingestion_partition` 或等价模型，字段至少包括：

- `ingestion_run_id`、`partition_key`、空间或分页参数；
- `status`、`attempt_count`、`next_retry_at`；
- `request_hash`、`parser_version`；
- `records_seen/created/updated/skipped/failed`；
- `started_at/finished_at/error_type/error_message`。

## 4. 开源项目的采用顺序

| 时点 | 参考重点 | 本项目动作 |
|---|---|---|
| 现在 | OSMnx、osmdata | 实现行政边界分片、请求缓存、状态感知和分片合并 |
| 紧接着 | Jye10032 的通用任务机制 | 实现有限重试、抖动、任务 metrics、失败重放；不采用登录和反爬部分 |
| 第二来源接入后 | dedupe | 用人工标注样本评估多字段实体匹配，和现有规则做基准对比 |
| 数据达到数万条后 | Splink | 评估概率链接、blocking 和诊断能力是否优于轻量规则 |
| 获得合规市场来源后 | 杭州/通用房产项目 | 借鉴小区—房源—快照—事件字段体系，不复用站点抓取实现 |

## 5. 下一步可执行任务

1. 先设计 `ingestion_partition` 状态机和唯一约束，再改 Overpass 查询；
2. 从西湖区边界生成 4 个固定测试分片，完成成功、超时、重试、断点续跑的集成测试；
3. 将 OSM 请求文本与 parser version 纳入哈希和快照元数据；
4. 让同一原始快照可以离线重复解析，并验证结果幂等；
5. 导出 50 个候选形成第一版实体分类和匹配标注集；
6. 为耀江文鼎苑建立第一条跨来源匹配解释，完整展示名称、地址、距离和人工结论；
7. 在此基础上再接第二来源，而不是先写另一套独立爬虫。

## 6. 边界

以上仓库只作为算法、任务编排、数据模型和质量控制的研究样本。具体实现应保持来源适配器可替换，并继续遵守项目既定边界：不绕过访问控制、不把挂牌当成交、不把规划当现状、所有外部事实保留来源和时间。
